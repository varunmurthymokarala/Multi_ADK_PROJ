1. Goals & Use Cases

🎯 Primary Goals

  • Reduce front-of-house load during peak hours
  • Convert browse-to-order in < 60 seconds
  • Reusable across many restaurants (multi-tenant)
  • Works embedded in any website, via QR, or PWA

🧑‍🍳 Customer Use Cases

  • "What's on the menu?" / "Any vegan options?"
  • "I want 2 margherita pizzas for pickup"
  • "How long is the queue right now?"
  • "Can I pay now and pick up later?"

🏪 Operator Use Cases

  • Onboard a new restaurant in < 30 min
  • Upload menu JSON/CSV → auto-vectorized
  • See live orders and chat history
  • Receive Stripe payments directly

5. ADK Agent Design

5.1 Orchestrator — single entry point

# core/agents/orchestrator.py
from adk import LlmAgent
from .menu_agent import menu_agent
from .order_agent import order_agent
from .payment_agent import payment_agent
from .queue_agent import queue_agent
from .faq_agent import faq_agent

orchestrator = LlmAgent(
    name="restaurant_assistant",
    model="qwen2.5-coder:7b",
    instruction="""
    You are the front-desk assistant for {tenant_name}.
    Classify each user message into ONE intent and delegate:
      MENU   -> questions about food, prices, allergens -> menu_agent
      ORDER  -> wants to buy or pickup -> order_agent
      PAY    -> wants to pay -> payment_agent
      QUEUE  -> asks about wait time -> queue_agent
      FAQ    -> hours, location, policies -> faq_agent

    Always confirm the cart total and pickup time before payment.
    Speak in {tenant_language}, be concise, friendly, never invent prices.
    """,
    sub_agents=[menu_agent, order_agent, payment_agent, queue_agent, faq_agent],
)

6. RAG & Vector DB Layer

6.1 Menu ingestion (one-time per tenant)

# core/rag/ingest.py
import chromadb, json
from .embeddings import embed

def ingest_menu(tenant_id: str, menu_path: str):
    client = chromadb.PersistentClient(path=f"tenants/{tenant_id}/vector_store")
    coll = client.get_or_create_collection(f"menu_{tenant_id}")

    menu = json.load(open(menu_path))
    docs, metas, ids, embs = [], [], [], []

    for item in menu["items"]:
        text = (f"{item['name']}. {item['description']}. "
                f"Price: $%7Bitem['price']%7D. Category: {item['category']}. "
                f"Allergens: %7B', '.join(item.get('allergens', []))%7D.")
        docs.append(text)
        metas.append({"price": item["price"],
                      "category": item["category"],
                      "available": item.get("available", True)})
        ids.append(item["id"])
        embs.append(embed(text))

    coll.upsert(documents=docs, metadatas=metas, ids=ids, embeddings=embs)
    return coll.count()

6.2 Retriever with metadata filters

# core/rag/retriever.py
def retrieve(tenant_id: str, query: str, k: int = 5,
             category: str | None = None, max_price: float | None = None):
    coll = get_collection(tenant_id)
    where = {"available": True}
    if category: where["category"] = category
    if max_price: where["price"] = {"$lte": max_price}

    return coll.query(
        query_embeddings=[embed(query)],
        n_results=k,
        where=where,
    )
Why chunk per menu item? Each item is a self-contained fact (~50–80 tokens). Items rarely need splitting, and metadata filtering by category/price becomes trivial.

# core/state/session.py
class Session:
    def __init__(self, session_id: str, tenant_id: str):
        self.id = session_id
        self.tenant = tenant_id
        self.redis = get_redis()

    @property
    def cart(self):
        return json.loads(self.redis.get(f"cart:{self.id}") or "[]")

    def add(self, item_id: str, qty: int, price: float):
        cart = self.cart
        cart.append({"item_id": item_id, "qty": qty, "price": price})
        self.redis.setex(f"cart:{self.id}", 1800, json.dumps(cart))

8. API Layer (FastAPI)

8.1 WebSocket chat endpoint

# api/routes/chat.py
from fastapi import APIRouter, WebSocket, Query
from core.agents.orchestrator import orchestrator
from core.state.session import Session

router = APIRouter()

@router.websocket("/ws/chat/{tenant_id}")
async def chat(ws: WebSocket, tenant_id: str,
               session_id: str = Query(...)):
    await ws.accept()
    sess = Session(session_id, tenant_id)

    while True:
        user_msg = await ws.receive_text()

        result = await orchestrator.run(
            message=user_msg,
            context={"session": sess, "tenant_id": tenant_id},
        )

        await ws.send_json({
            "text": result.text,
            "cart": sess.cart,
            "actions": result.tool_calls,   # UI buttons (e.g. "Pay $24.50")
        })

9. MCP Servers (Payments, POS, More)

9.1 Stripe MCP — payment links

# mcp_servers/stripe_mcp/server.py
from mcp.server import Server
from mcp.types import Tool, TextContent
import stripe, os

server = Server("stripe")
stripe.api_key = os.environ["STRIPE_SECRET_KEY"]

@server.tool()
async def create_payment_link(amount_cents: int,
                              description: str,
                              metadata: dict) -> list[TextContent]:
    link = stripe.PaymentLink.create(
        line_items=[{
            "price_data": {
                "currency": "usd",
                "product_data": {"name": description},
                "unit_amount": amount_cents,
            },
            "quantity": 1,
        }],
        metadata=metadata,
    )
    return [TextContent(type="text", text=link.url)]

11. Multi-Tenant Strategy

Tenant isolation

  • Each tenant gets a folder under tenants/
  • ChromaDB collection name = menu_{tenant_id}
  • Postgres row-level filter on tenant_id for orders
  • Redis keys prefixed with tenant

Onboarding a new restaurant

  1. Generate tenant_id (UUID)
  2. Create folder, drop menu.json + config.json
  3. Run python -m core.rag.ingest {tenant_id}
  4. Issue API key, point Stripe account
  5. Give them the widget snippet + QR PNG

⏱️ Total time: ~15–30 minutes.

12. Security & Observability

🔒 Security

  • Tenant auth — API key per restaurant; widget sends hashed key
  • Session tokens — short-lived JWT for customer sessions
  • Rate limits — 30 msg/min per session via Redis token bucket
  • PII — never log full prompts; redact phone/email in transcripts
  • Stripe webhook — verify signature; idempotency keys
  • MCP isolation — each tenant's MCP server uses their own Stripe account

📈 Observability

  • Structured JSON logs (structlog) → stdout → Loki
  • OpenTelemetry traces for each agent tool call
  • Langfuse (optional) for LLM trace inspection
  • Prometheus metrics: orders/day, p95 latency, tool error rates
  • Cost guardrails — token usage per tenant, alerts at thresholds

13.2 Scaling path

  1. Phase 0–1: Single VPS, all containers, Ollama on same host (GPU optional)
  2. Phase 2: Move Ollama to dedicated GPU box, keep API stateless behind load balancer
  3. Phase 3: Horizontal API replicas, Chroma cluster mode, Postgres → managed (RDS/Neon)

15. Pre-Build Checklist

Confirm these before writing code:

  • Decide on language(s) for menu + chat (English first, multi-lang later)
  • Get Stripe test account → secret key + webhook secret
  • Confirm embedding model runs on your hardware (CPU OK at small scale)
  • Decide on Postgres hosting (Docker locally, Neon/Supabase in prod)
  • Buy/point a domain (e.g. chat.yourcompany.com) + TLS cert
  • Design the menu JSON schema (see §11) — get buy-in from a pilot restaurant
  • Choose vector DB host path: per-tenant folder vs single Chroma with namespacing
  • Decide on observability stack (start simple: JSON logs + Grafana Cloud free tier)
  • Pick a notification provider for order-ready (web-push first, SMS via Twilio later)
  • Draft the system prompt for the orchestrator with one pilot restaurant's voice
⚠️ Gotchas to avoid
  • Don't let the LLM invent prices — always require a tool call to look up price
  • Never trust client-side cart totals — recompute server-side at checkout
  • Stripe webhook must be idempotent (payment intent can fire twice)
  • Ollama cold-start is slow (~3s) — keep API process warm, pre-load model
  • Chroma persists per folder — back up tenants/ directory regularly
